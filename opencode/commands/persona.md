## Context

You are defining a user persona for project **{{project_name}}** to ground UI/UX decisions in real
user context. The persona lives at `.claude/personas/{{input.name | slugify}}.md` and is loaded
by `/prd`, `/proto`, and `/component` when present — it is NOT auto-imported into CLAUDE.md.

A persona is a **design tool**, not a marketing artifact. It should surface the constraints,
mental models, and failure modes that affect UI decisions — not aspirational copy.

---

## Step 0 — Scope check (ask if missing)

Before generating, verify you have enough signal for a grounded persona. If any of the following
is ambiguous, ask (accept terse 1–2 word answers):

```
Quick scope check:
Role?       [what does this person DO in the product — not their job title]
Context?    [when/where do they use it — desktop, mobile, on-the-go, daily/weekly]
Goal?       [the ONE thing they come to accomplish]
Blocker?    [what frustrates or slows them down today]
```

If the user says "you decide" → make reasonable defaults and STATE them explicitly.

---

## Step 1 — Ground the persona (before writing)

Check the project for existing signal:

1. **Read `tasks/prd-*.md`** — PRDs often name a role in §3 JTBD or §2 evidence. Extract any
   stated user type, pain point, or context clue. Tag each claim `observed` (found in PRD/code)
   or `assumed` (inferred).
2. **Check `.claude/personas/`** — if a persona for this role already exists, ASK before
   overwriting. Offer to update instead.
3. **Check for domain signal** — does the project have user-facing copy, onboarding flows, or
   existing components that reveal assumed mental models? Read 1–2 representative screens if they
   exist.

---

## Step 2 — Generate the persona file

Write a persona file with the following sections. Every claim must be tagged `observed` or `assumed`.

```markdown
# Persona: {{input.name | titlecase}}

> **Role in product:** [what they DO, not their job title]
> **Confidence:** [HIGH / MED / LOW — how grounded this persona is vs. assumed]

---

## 1. Snapshot
| Field        | Value |
|--------------|-------|
| Role         | [e.g. marketplace buyer, school admin, API consumer] |
| Context      | [when/where/device — e.g. "mobile, commuting, 3x/week"] |
| Tech fluency | [low / medium / high — affects copy density + affordances] |
| Session goal | [the ONE thing they come to do] |

## 2. Jobs to be Done (top 3)
1. When [situation], I want to [motivation], so I can [outcome]. `[observed|assumed]`
2. …
3. …

## 3. Pain Points & Blockers
What slows them down or causes failure today — constraints that MUST shape UI decisions.

- [Pain 1] `[observed|assumed]`
- [Pain 2] `[observed|assumed]`
- [Pain 3] `[observed|assumed]`

## 4. Mental Model
How they think about the domain — what vocabulary, metaphors, or expectations they bring.
Wrong mental model = confusing UI even if technically correct.

- [Key mental model or assumption they hold] `[observed|assumed]`
- …

## 5. UI/UX Constraints
Direct constraints on design decisions — NOT preferences. These are the things that, if violated,
cause confusion, abandonment, or errors.

| Constraint                        | Implication for UI                  |
|----------------------------------|-------------------------------------|
| [e.g. Low tech fluency]           | [Avoid jargon; use familiar metaphors] |
| [e.g. Mobile + intermittent data] | [Offline states, small payloads]    |
| [e.g. Time-pressured context]     | [No multi-step flows for core action] |

## 6. What They Must NEVER Experience
The failure modes that cause abandonment, support tickets, or broken trust. Design reviews
should check these explicitly.

- [e.g. "Losing unsaved work"] — every form has autosave or draft state
- [e.g. "Unclear error messages"] — errors name the field + recovery action
- …

## 7. Evidence & Sources
| Claim | Source | Tag |
|-------|--------|-----|
| [claim] | [PRD §2 / user interview / analytics / assumed] | [observed\|assumed] |

---

*Generated by `/persona`. Update when user research surfaces new signal.*
*Loaded by: `/prd` (§2 evidence), `/proto` (UI state design), `/component` (props + copy decisions).*
```

## Step 3 — Quality check (Blocking Set must be empty before saving)

**Gate = the Blocking Set is empty.** Every row below is a Blocking predicate — resolve all before saving
the persona. The Severity column is a fix-order hint (fix larger first), **not a summand**. Genuine cosmetic
polish not in this table stays Advisory and never gates.

| Blocking predicate (resolve before saving) | Severity (fix-order hint — NOT summed) |
|---------------------------------------------|----------------------------------------|
| Snapshot missing any field | −5 each |
| JTBD not in Klement form ("As a…" persona story instead) | −10 |
| Pain points stated as features ("they want X") not blockers ("they fail because Y") | −5 each |
| UI/UX Constraints table empty | −15 |
| "Must never experience" section empty | −10 |
| Every claim is `assumed` with no grounding attempt (Step 1 skipped) | −20 |
| Mental model section empty or just restates the role | −10 |

**Gate:** Blocking Set empty → save. Any Blocking predicate unresolved → fix, then save. If most rows are unresolved → return to Step 0.

---

## Step 4 — Save and register

1. Save to `.claude/personas/{{input.name | slugify}}.md`.
2. Check if `.claude/CLAUDE.md` exists in the project:
   - If yes: add a comment block at the bottom noting the persona file exists.
     Do NOT auto-add `@import` — the user decides which personas are always-on.
   - If no: skip.
3. Print the wiring instruction:

```
Persona saved: .claude/personas/{{input.name | slugify}}.md

To activate for all tasks in this project, add to .claude/CLAUDE.md:
  @.claude/personas/{{input.name | slugify}}.md

Or leave unregistered — /prd, /proto, and /component will check for it explicitly.
```

---

## How downstream skills use this persona

When a skill (`/prd`, `/proto`, `/component`) runs, it should:

1. **Check** if `.claude/personas/*.md` exists in the project.
2. **Read** the matching persona(s) before making UI/copy/layout decisions.
3. **Cite** the persona section that drove a decision (e.g. `→ persona §5: mobile context`).

This is opt-in per-skill — not auto-loaded — to keep context lean.

---

## Anti-patterns (reject on sight)

| Anti-pattern | Fix |
|--------------|-----|
| "Sarah, 32, loves coffee" demographic fluff | Replace with behavioral signal: what she DOES, not who she IS |
| Pain points stated as feature requests ("wants dark mode") | Restate as failure mode: "abandons after 10min eye strain on long sessions" |
| 100% `assumed` with no grounding attempt | Run Step 1 first; label honestly |
| Constraints section says "good UX" | Name specific constraints: "must work on 3G", "no technical jargon" |
| JTBD in persona form ("As a buyer, I want…") | Rewrite in Klement format |
