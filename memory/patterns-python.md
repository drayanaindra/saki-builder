# Python / FastAPI / SQLAlchemy Patterns

Stack-specific patterns for Python, FastAPI, SQLAlchemy/Alembic, and async Python. Loaded on-demand via `@import` in project CLAUDE.md files that use this stack.

---

## Python / API

- **When extracting a Python helper above a decorated function, anchor the Edit on the DECORATOR line, not the `def` line**: Anchoring the insertion point on `async def route_handler(` (or any decorated function's `def` line) places the new helper BETWEEN the decorator and the `def`. Python applies the decorator to the next function it encounters — which is now the helper, not the handler. The handler is silently un-decorated (missing auth, missing type constraints, wrong return type). The bug is silent in local tests if they call the handler directly without going through the router. Always anchor on the `@decorator(...)` line above the function you're inserting before; the decorator stays on the right target. (confidence: HIGH, source: 1 project — failure mode was silent wrong route registration caught only in integration tests, date: 2026-06-06)
- **Bulk string replacement breaks Python implicit concatenation**: Python fuses adjacent string literals at compile time (`"str1" "str2"` → one string). Replacing only `"str1"` with a constant drops the implicit join — `CONST "str2"` is a SyntaxError (or silently wrong at the value level). Before doing any bulk string find-replace: scan the surrounding context for adjacent literals. If found, use explicit `+` concatenation after substitution: `CONST + "str2"`. Most common source of breakage: auto-refactor scripts that don't read multi-line context. (confidence: HIGH, source: SonarQube S1192 bulk fix session, date: 2026-05-22)
- **Script insertion at "last import line" fails for multi-line parenthetical imports**: A script that finds the last line matching `^from … import` and inserts after it will land INSIDE an open parenthetical block like `from app.schemas import (\n    A,\n<INSERT>\n    B\n)` → SyntaxError. Must track paren/bracket depth and only insert when depth is zero. Template: iterate lines, maintain `depth += open - close`; insert only when `depth == 0 and re.match(r'^from |^import ', line)` and the NEXT non-empty line is not another import. (confidence: HIGH, source: SonarQube S1192 bulk fix session, date: 2026-05-22)
- **`python -m py_compile file.py && echo OK` is the fastest syntax gate after scripted file transforms**: Run it on every touched file before `git add`. Catches self-referential constant assignments (`CONST = CONST`), decorator misplacement, and truncated string replacements in <1s. Cheaper than a full `pytest` run and catches the class of bugs that scripted bulk edits most commonly produce. (confidence: HIGH, source: 2 SonarQube bulk-fix sessions, date: 2026-05-22)
- **Pydantic response models must not inherit input validators**: Response schemas with `min_length`, `regex`, or other input constraints crash the entire list endpoint if ANY single DB row violates the constraint — one bad row = 500 for all users. Keep strict validation on input schemas only; response models should be lenient. (confidence: HIGH, source: production incident — list endpoint 500, date: 2026-03-09)
- **`server_default` required for non-nullable columns on existing tables**: When adding a non-nullable column to a table that already has rows, set both `default=` (Python ORM) AND `server_default=` (DB-level). Missing `server_default` causes the migration to fail on non-empty tables even if `default=` is set. (confidence: HIGH, source: multiple projects — Alembic + SQLAlchemy, date: 2026-03-09)
- **Alembic `--autogenerate` picks up ALL schema drift, not just intended changes**: Always inspect and clean generated migrations before applying — remove unintended table/column changes that drifted since last migration. Apply only the target change. (confidence: HIGH, source: multiple projects — confirmed across 2 codebases, date: 2026-03-09)
- **`smtplib.SMTP(host, port)` has NO default timeout — always pass `timeout=10`**: Default is OS-level socket timeout (potentially minutes on Linux, infinite on some configs). If the SMTP relay is unreachable, the worker hangs until gunicorn's worker-timeout kills it (default 30s). Combined with `await` of a sync smtplib call inside a request handler, that surfaces as a 502 *after* `db.commit()` already changed state — silent data divergence. One-line fix: `smtplib.SMTP(host, port, timeout=10)`. Same applies to `smtplib.SMTP_SSL`. (confidence: HIGH, source: 1 project + applies broadly, date: 2026-05-03)
- **FastAPI `BackgroundTasks` runs SYNCHRONOUSLY on the same event loop after the response**: It does NOT take blocking I/O off the loop — it just defers it past the response send. If your background callable is sync (smtplib, sync HTTP libraries), the loop is still pinned for the call duration after the response is sent, blocking other requests on the same worker. To actually run off-loop: (a) wrap the sync call inside `asyncio.to_thread(fn, *args)` in your background task, OR (b) declare the background callable as plain `def` (not `async def`) — FastAPI runs sync background callables in a threadpool via `run_in_threadpool`. Inline `await sync_fn()` at low volume (<5/day) is acceptable if the sync call has a short timeout cap. (confidence: HIGH, source: 1 project + applies to any FastAPI app, date: 2026-05-03)
- **`pg_insert(...).on_conflict_do_nothing(index_elements=['x'])` against a partial UNIQUE index requires `index_where=`**: Postgres needs the partial-index predicate to match the index as the conflict target. With only `index_elements`, runtime raises SQLSTATE 42P10 "no unique or exclusion constraint matching the ON CONFLICT specification". Correct: `pg_insert(Model).on_conflict_do_nothing(index_elements=['user_id'], index_where=Model.user_id.isnot(None))`. The pseudo-SQL form `ON CONFLICT (user_id) WHERE user_id IS NOT NULL DO NOTHING` is correct; the SQLAlchemy call must mirror both clauses. (confidence: HIGH, source: 1 project but applies to all SQLAlchemy + Postgres, date: 2026-05-03)
- **`Base.metadata.create_all` builds test schema from MODEL definitions, NOT from migrations**: Tests that use `await conn.run_sync(Base.metadata.create_all)` create a synthetic schema that includes every column/constraint declared on the model — even ones that were never migrated to production. Model→migration drift (e.g. an uncommitted `UniqueConstraint` in `__table_args__`) passes tests but breaks in prod. When verifying schema-level invariants (unique constraints, CHECK constraints, foreign keys), always run `\d table` against the live DB or against an alembic-built test DB — never trust model declarations alone. (confidence: HIGH, source: 1 project + applies to any SQLAlchemy + alembic project, date: 2026-05-03)
- **Alembic `upgrade()` needs an IF NOT EXISTS guard when the table may already exist**: If a table was created manually (dev hotfix, prior partial migration, or ORM auto-create at startup) before the migration is written, `op.create_table()` raises `DuplicateTableError`. Guard with: `inspector = sa.inspect(op.get_bind()); if "table_name" not in set(inspector.get_table_names()): op.create_table(...)`. Mirror the guard in `downgrade()` for safety. Applies to both `op.create_table` and `op.create_index`. (confidence: HIGH, source: confirmed 1 project; applies to any Alembic + Postgres/SQLite project, date: 2026-05-21)
- **FastAPI `app.dependency_overrides[get_db]` does NOT patch `async_session_factory` direct callers**: `dependency_overrides` only intercepts code that goes through FastAPI's DI graph (i.e. `Depends(get_db)`). Background tasks or service methods that call `async with async_session_factory() as db:` directly bypass DI entirely — they get a real production DB session even during tests. Fix: `patch("module.async_session_factory", in_memory_factory)` at the test level for each module that uses the factory directly. (confidence: HIGH, source: confirmed across 2 projects — same pattern needed for background tasks and non-request lifespan hooks, date: 2026-05-21)
- **Green test suite can pass while the running dev app 500s — the dev DB lags *applied* migrations**: pytest builds a fresh schema per run (`Base.metadata.create_all` on a throwaway test DB), so the suite is green against the current model schema. The long-lived *dev* DB only has whatever migrations were actually run against it — after multi-feature/multi-migration work it can be missing real columns/tables the current code selects (a `SELECT *`-style ORM load of a row whose newly-added column the dev DB lacks → `UndefinedColumnError` 500, even though there's no model→migration drift). Distinct from the create_all-vs-migration-INVARIANT drift entry above: here the migrations are correct, they were just never run on this DB. After cross-migration work, smoke the RUNNING app (hit a couple of endpoints), not just the test suite. To resync a dev DB to ORM truth without fighting a broken/multi-head alembic history (multiple `heads` + duplicate revision ids make `upgrade head` unsafe): `ALTER TABLE … ADD COLUMN IF NOT EXISTS` for drifted columns + `Base.metadata.create_all(checkfirst=True)` for missing tables (import the app first so every model registers); leave proper alembic repair (dedupe revision, merge heads, `stamp`) as its own task. (confidence: HIGH, source: confirmed 2× on same project, stack-portable to any pytest-create_all + Alembic-migrated-dev-DB setup, date: 2026-06-22 → 2026-06-25)

## Python Async

- **`asyncio.to_thread()` / `run_in_executor()` for any synchronous call in async context**: Never call synchronous operations directly in an async handler — blocks the event loop for all concurrent requests. Rule: **CPU-bound sync (ML inference, compression)** → `await asyncio.to_thread(fn, *args)`. **I/O-bound sync SDK (boto3, stripe, any sync HTTP client)** → `await loop.run_in_executor(None, partial(fn, **kwargs))`. For startup preloading, use `loop.run_in_executor(None, preload_fn)` in the lifespan handler to avoid cold-start delay. (confidence: HIGH, source: multiple projects — 2 different contexts confirmed, date: 2026-03-11)
- **`except Exception` misses `CancelledError` in Python 3.8+**: `CancelledError` is `BaseException`, not `Exception`. In startup/lifespan safety nets and reconnect loops, always use `except BaseException` to prevent silent crash propagation. Real production impact: FastAPI backend crashed at startup every time an external service was unreachable. (confidence: HIGH, source: multiple projects — lifespan + reconnect patterns, date: 2026-03-10)
- **anyio cancel scope must be entered/exited in the same asyncio Task**: When `anyio.create_task_group()` is used inside an async context manager, entering via `__aenter__()` in one task and exiting in another raises `RuntimeError: Attempted to exit cancel scope in a different task than it was entered in`. Fix: run each anyio-dependent operation in its own `asyncio.create_task()`. (confidence: HIGH, source: multiple projects — MCP/SSE client pattern, date: 2026-03-10)
- **Async SQLAlchemy: every relationship a service reads must be explicitly eager-loaded by every caller**: When a pure service function reads `obj.foo.bar`, every endpoint/caller that hands it an `obj` must include `selectinload(Model.foo)` (or equivalent) in its query. Async sessions raise `MissingGreenlet` on lazy-load. **Identity-map can mask the bug** — if the parent of `obj.foo` is already loaded for another reason (e.g. you walked `Parent → children`, and `children[i].parent` resolves via session cache), it works without IO until a refactor changes the load path. Then it explodes in production. Three known triggers: (1) `expire_all()` in async context forces sync lazy-load; (2) downstream service reading nested relationship that wasn't in the caller's selectinload chain; (3) **`db.commit()` with default `expire_on_commit=True` expires every attribute on the loaded object — `model_validate(obj)` immediately afterward triggers MissingGreenlet on EVERY field** (not just relationships). Fix for case (3): `await db.refresh(obj, ['relationship_a', 'relationship_b'])` after commit before serializing, OR re-fetch the row with a fresh `select(...).options(selectinload(...))`. Always trace: which fields does the service touch? Each one needs an explicit selectinload at the call site, AND any post-commit serialization needs an explicit refresh. (confidence: HIGH, source: confirmed 4× across 3 sessions on same backend project, date: 2026-05-03)
