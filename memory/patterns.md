## Workflow

- **QA: classify acceptance criteria as automatable vs manual**: After implementation, read the plan's success criteria and split into two buckets: (1) *Automatable* — verify with curl/grep/jq/file check (HTTP status, JSON shape, file existence, env var presence); (2) *Manual-only* — requires human/browser (UI rendering, auth flows, AI output quality, form interactions). Run automatable checks immediately. Write manual-only criteria to a `[task]-qa.md` checklist file so they aren't forgotten. (confidence: HIGH, source: confirmed across multiple projects, date: 2026-03-14)
- **Research > Discuss > Map > Implement**: Never jump to implementation. Establish foundations first — research the domain, discuss with user to align, map the solution, then build. (confidence: HIGH, source: multiple projects, date: 2026-03-08)
- **4-gate plan review — confidence alone is insufficient**: A plan passes review only when all 4 gates are met: (1) confidence >= 96%, (2) User Role Coverage matrix (every role with full call chain + auth guard), (3) Plan Wiring (each major flow written as `Component → api.ts function → HTTP METHOD /path → service.function() → Model.field`), (4) Migration Checklist (every schema change has named migration file + command). Confidence-only review misses unimplemented roles, missing migrations, and broken wiring. Observed failure modes: admin endpoint implemented but customer endpoint missing; migration step omitted from plan; step says "update frontend" without naming file/function. (confidence: HIGH, source: confirmed across multiple projects — 2 separate corrections, date: 2026-03-15)
- **Full-stack field addition order that minimizes rework**: model → schema → service → API route helper → API route endpoint → migration → frontend types → frontend UI. Going frontend-first or migration-first causes rework when the model shape turns out different than expected. (confidence: HIGH, source: confirmed 2× sessions on the same project, date: 2026-03-09)
- **Subagent size threshold for research**: ≥8 files across frontend+backend → use Explore subagent (one-pass comprehensive context). ≤4 specific, known files → use Read/Grep directly (subagent overhead not worth it). (confidence: HIGH, source: multiple projects — 3 separate tasks confirmed, date: 2026-03-09)
- **Verify code state, not plan file status**: Plan files can say "Draft" or "In Progress" while the code is already fully implemented. Always read the actual source files to verify implementation state before starting — avoids re-doing work. (confidence: MED, source: multiple projects — 2 separate tasks, date: 2026-03-09)
- **Multiple `/rplan-review` passes catch layered bug classes**: A single review pass is insufficient. Each pass finds a different category: Pass 1 catches safety/correctness issues (infinite recursion, auth ambiguity, missing guards). Pass 2 catches implementation ambiguity (redirect ownership, internal flag mechanisms, await-vs-fire-and-forget timing). Pass 3 catches logic bugs (JS truthiness traps, missing SQL clauses like RETURNING). When user requests a second review, it is always productive — never skip it as redundant. (confidence: HIGH, source: confirmed across 3 sessions on a multi-tenant SaaS project, date: 2026-03-29)
- **`/rplan-review` score trajectory is itself a convergence signal**: Track the score across rounds. Round-1 score X% → round-2 score Y% with `Y > X` AND fewer/lower-level blockers = converging, ship. `Y ≈ X` AND new blockers at the same level = recut scope, do not run round 3. Real example: 30% → 56% → 73% → 96% across 4 rounds = converged via real fixes; if round 3 had been 56%-stuck-with-same-volume-of-blockers, the right call would have been recut at that point, not round 4. (confidence: HIGH, source: confirmed across multiple projects, date: 2026-05-03)
- **Senior-PM peer review BEFORE shipping when scope fights PRD appetite**: When a plan exceeds its PRD-stated appetite (e.g. PRD §6 says "~4 tasks, recut threshold at 6" but plan is 12), spawn a `senior-pm` subagent with explicit pressure-test questions ("is this cut load-bearing?", "what cuts would you reverse?", "what triggers the deferred phases?") — not "review my plan". Returns reverses on over-aggressive cuts AND pushes correct deferrals. Highest-leverage PM intervention available. (confidence: HIGH, source: confirmed across multiple projects, date: 2026-05-03)
- **Recut > fix-then-fix when blockers accumulate across review rounds**: When `/rplan-review` rounds 1+2 surface 17+ cumulative blockers and the plan is N× over PRD appetite, the load-bearing problem is scope, not implementation gaps. The right move is recut into trigger-gated phases (B → B1+B2+B3 with objective signals like "first dup-row logged", "outcome 5.1 <70%"), not deeper revisions of the same plan. Each revision adds drift faster than it removes blockers. (confidence: HIGH, source: confirmed across multiple projects, date: 2026-05-03)
- **Phase-gate triggers tied to objective signals prevent perpetual deferral**: When deferring scope to "B2 / B3 / later", define each phase's trigger as a measurable signal in production logs/queries (e.g. "B2 ships when first dup-seller row logged OR ≥3 concurrent admins" / "Slice C ships when cohort resubmit-rate <50% within 14 days"). Better than calendar-based ("ship in 2 weeks") or vague-volume ("when needed") thresholds — the trigger fires automatically when the underlying problem appears. (confidence: HIGH, source: confirmed across multiple projects, date: 2026-05-03)
- **Operational owner pin in plan No-Gos as dashboard substitute**: At MVP scale, replace "build a metrics dashboard" with `Owner: @name. Cadence: weekly. SQL snippet: <queries>`. Cheaper than a dashboard, tighter than "monitor somehow"; PRD kill-criterion provides the hard backstop. Only escalate to dashboard when volume justifies (≥2 reviewers, weekly throughput pressure). (confidence: HIGH, source: 1 project, but pattern is generic, date: 2026-05-03)
- **Don't fix unrelated infra mid-PRD — document the workaround, apply per-instance**: When you discover a known infra bug (test conftest event-loop mismatch, broken venv symlinks, schema drift) while starting a new PRD's first slice, the cost of detouring to fix it is 1+ days plus its own ripple-fix tail in unrelated files. The right move: document the workaround in CLAUDE.md (or a `patterns-<topic>.md`) ONCE, then apply the per-instance pattern in every new file across the PRD. A multi-slice PRD that uses the workaround verbatim 8 times costs less than the "fix the infra" side-quest. Trap signal: "we should really fix this conftest thing" — that's exactly when to add it to CLAUDE.md and keep moving. (confidence: HIGH, source: confirmed across 3 sessions on 1 project, date: 2026-05-11)
- **Registry sentinel test design: pick a never-registered key on the first test, not a real future name**: Registry dispatch tables (carrier → client, intent → handler, payment-method → gateway, mime-type → parser) accumulate entries over time. The "unsupported-key returns failure" test gets edited every time a new entry joins IF the test used a real next-up name as its placeholder. Pick a sentinel that's intentionally never going to be a real registered key (`"unknown_carrier"`, `"__unused__"`, `"sentinel_unregistered"`) on the FIRST registry test. Saves a one-line edit on every subsequent expansion — and more importantly, removes a recurring source of "did I forget to update the sentinel test?" mistakes in PRs that add registry entries. (confidence: HIGH, source: 1 project but confirmed 3× via ripple-fix pain across slices, date: 2026-05-11)
- **Cap checks at write-time don't cover concurrent pending-state bypass**: When an abuse guard checks a count (e.g. qualified referrals) at item-creation time, concurrent items created before any qualify all pass the check. Add a second cap check at the state-transition event handler (e.g. qualification subscriber) to enforce the limit at the point where the count actually increments. Mark items' status correctly (honour the user action) but withhold the downstream side-effect (reward, credit) if over cap. (confidence: HIGH, source: edbot-workspace-3 E24 reviewer — confirmed generic pattern, date: 2026-05-28)
- **Pin the source state when verifying a claim ("does X exist / does this constraint hold?")**: Check it against an EXPLICIT, pinned source — a committed diff at a base ref (`git diff <BASE>..HEAD`), or the specific target/build branch (`git ls-tree -r <branch> -- <path>`, `git show <branch>:<path>`) — never an incidental view: the open working tree, an aggregate integration branch, or whichever checkout happens to be open. Incidental views carry uncommitted edits or cross-branch state that silently falsify the check. Observed failure modes: a reviewer "confirmed" a UNIQUE constraint that was only an uncommitted working-tree edit (not migrated); a PRD claimed a module was REAL by reading an arbitrary checkout when it lived only on another feature branch; planning read a file from an aggregate branch whose content differed from the actual build base; a tracker board said an epic was "Done — all tests pass" while its branches existed ONLY locally (never pushed) and carried failing tests — the integration script silently merged origin's stale ref, producing a no-op integration that looked successful. Boards record claims; `git log origin/<branch>` + a test rerun record state. (confidence: HIGH, source: confirmed across 3 projects, date: 2026-05-24, strengthened 2026-06-06)
- **Reuse-first + ownership check BEFORE designing/building, not just before implementing**: the moment a "build/support X" request lands — before writing any PRD/plan or scaffolding — confirm X doesn't already exist and isn't already owned. (1) *Does it already exist?* grep existing specs/roadmap/models/components and read library defaults — a component can sit in `components/` yet be missing from `index.ts`; a domain entity often has a first-class model + admin page; a library feature may be on-by-default (read the dist, don't assume it needs building). (2) *Is it already planned/in-flight?* read the actual spec file + tracker, not the one-line summary — a board row can say "TBD" while its spec file is 150–200 lines and fully fleshed. (3) *Is it OWNED?* check the STATUS/owner column; if a teammate has it claimed, go ADVISORY (share findings, hand off) — never claim, build, or edit their artifacts. Skipping this repeatedly burned full design/build cycles: a duplicated in-review MR; a whole capstone PRD that duplicated an already-planned epic family AND collided with teammate-owned, product-locked epics; a freeform input form rebuilt onto an existing first-class model. Distinct from "verify a dependency's status against git" (that's a dep's *state*) — this is about not rebuilding or colliding with work that already exists or is owned. (confidence: HIGH, source: confirmed across 3 projects, date: 2026-05 → 2026-06-16)
- **Green unit tests ≠ robust for a process-spawning / retry-loop engine — run an adversarial pressure-test before declaring done**: After the unit suite passes, spawn 2+ PARALLEL adversaries that TRACE THE ACTUAL CODE (cite line numbers), each hunting a failure class tests rarely cover: unbounded/runaway spawn, double-spawn (in-memory timer + poll sweep + manual path racing on one item), durable state lost in a restart-mid-window, budget bypass, and classification holes (false terminal / false retry). On a real auto-resume engine this surfaced 6 edge bugs *after* 200+ green tests (silent lost-resume on a spawn throw, a watchdog over-killing legit-slow work, no SIGKILL escalation, regex false-positives). Then LOCK the safe properties you verified (no-runaway-across-restart, loop-bounded-by-cap, no-double-fire) with regression tests so they can't silently regress. Adjacent to "Test doubles validate structure, NOT live behavior" — green tests prove the unit, not the loop's emergent safety. (confidence: HIGH, source: 1 project, date: 2026-06-29)

## Code Quality

- **Never use `transition-all` on interactive cards/toggles**: Use `transition-colors` or list specific properties. `transition-all` animates width/height/shadow changes causing layout jank, especially in grid layouts. (confidence: HIGH, source: multiple projects, date: 2026-03-08)
- **Tailwind `focus:ring-offset-*` adds real box space**: Avoid on elements inside constrained grids/flexbox — it pushes parent containers wider on focus. Use `focus:ring` without offset, or `focus:outline` instead. (confidence: MED, source: multiple projects, date: 2026-03-08)
- **`html.escape()` user-controlled strings before HTML interpolation**: Any user-controlled or admin-authored string interpolated into f-string HTML (email templates, server-side renders, debug pages) needs `html.escape(s)` first. Modern webmail strips `<script>` so this is rarely full XSS, but it IS unwanted HTML reflection — `<a>` injection, `<img onerror=>` payloads, broken layout. Especially dangerous for fields populated by users (full_name, listing_title, reject_reason). Same rule for any string going into HTML attribute context (use `quoteattr` semantics). (confidence: HIGH, source: 1 project + multi-domain rule, date: 2026-05-03)
- **`getComputedStyle` > screenshots for visual-parity / refactor verification**: When verifying a CSS refactor (especially one that drops style declarations on an outer wrapper), assert with `getComputedStyle(el).getPropertyValue('background-color')` etc. — NOT screenshots. Cream-on-white bg, dark-brown vs pure-black text, 13px vs 16px are near-indistinguishable in PNGs at typical zoom; computed-style strings are exact. Screenshots are supplementary, not load-bearing. Before deleting an outer-wrapper style declaration, grep `body`/`global.css` to check whether the property is declared at root — children typically inherit from `body`, which falls back to browser defaults (white bg, black text, 16px) if not set. (confidence: HIGH, source: confirmed 2× on same project, date: 2026-05-08 → 2026-05-09)
- **Test doubles validate code structure, NOT live DB behavior**: Mocked DB layers and synthetic test schemas (mocked Mongoose/ORM model statics; `Base.metadata.create_all` built from models; in-memory SQLite) exercise the *query/declaration you construct*, never the real datastore's runtime behavior. So pipeline/aggregation semantics, upsert idempotency, unique-constraint insert races, schema invariants (UNIQUE/CHECK/FK), and model→migration drift all pass mocked tests but can break against prod. Assert what the mock genuinely proves (the shape of the query/pipeline you send, the mapper/DTO output), then DEFER the data-behavior verification to a check against a real local DB before merge — never report "verified" for data semantics from mocked tests alone. (confidence: HIGH, source: confirmed across 2 projects / 2 stacks — ORM+migrations and a document DB, date: 2026-05-24)
- **SQLite: control timestamps in application code, not the DB**: SQLite has no native datetime type (stores text/numbers, no timezone). `DEFAULT CURRENT_TIMESTAMP` returns `'YYYY-MM-DD HH:MM:SS'` which breaks Go `time.Time` scanning; and a `DateTime(timezone=True)` column still returns NAIVE datetimes, so Python `datetime.now(UTC) - row.ts` raises `TypeError`. Generate timestamps in the app as explicit UTC (`time.Now().UTC().Format(time.RFC3339Nano)` / store ISO-8601), and on read normalize tz (`dt.replace(tzinfo=UTC) if dt.tzinfo is None`). Bites hardest in tests (in-memory SQLite stores naive even when the column is tz-aware). (confidence: HIGH, source: confirmed across 2 projects / 2 languages on SQLite, date: 2026-05-24)
- **Anchor regex to line-start when matching a TOOL's output that shares one stream with the MODEL's prose**: Parsing combined `cmd 2>&1` / stream-json where a CLI's sentinels/status lines are interleaved with model narration → anchor patterns to line-start (`/^\s*.../m`). The tool prints its markers as STANDALONE lines; the model narrates the same words mid-sentence ("…slice 4 is BLOCKED: on an API", "the usage-limit-reached handler is done"). Unanchored substring matching → false classification: a narrated "BLOCKED:" wrongly marks an incomplete run terminal; a mentioned "usage limit" triggers a wrong long retry-wait. Same family as the "escape/anchor untrusted strings before interpolation" caution — here the untrusted-but-mixed-in text is the model's own output. (confidence: HIGH, source: 1 project, date: 2026-06-29)

## Tools

- **Reading PDFs: WebFetch saves binary, use pdftotext**: WebFetch downloads PDFs as binary to a local path but can't extract text. Install poppler (`brew install poppler`) then run `/opt/homebrew/bin/pdftotext file.pdf -` to extract text. `pdftotext` is NOT in default shell PATH. (confidence: HIGH, source: research session, date: 2026-03-09)
- **Monitor tool for CI polling — not Bash sleep loops**: Waiting for CI to finish: use `Monitor` with a poll loop that emits a line on state change and `break`s on terminal states (success|failed|canceled). Never chain `sleep N && glab ci list` — the harness blocks long sleeps. Pattern: `while true; do result=$(glab ci list...); echo "$result"; echo "$result" | grep -qE 'success|fail' && break; sleep 20; done`. A `run_in_background` Bash poll loop that exits on terminal state is an equivalent non-blocking option — the harness re-invokes you when the background command exits. (confidence: HIGH, source: harness behavior, date: 2026-05-27)

## Debugging

- **Empty catch blocks = invisible bugs**: `catch { return; }` or `catch {}` in async init/setup makes it impossible to diagnose which stage fails. Always log `console.warn(err)` at minimum in every catch block, even for "non-critical" features. Real impact: hardware-delegated API (e.g. MediaPipe) failed silently at 3 different stages with no way to distinguish them. (confidence: HIGH, source: multiple projects — 2 sessions, date: 2026-03-08)
- **Browser cache first for "stuck loading" web debugging**: Frontend "stuck loading" with healthy vite process + healthy backend API = almost always a browser cache issue. `Cmd+Shift+R` (hard reload) is the first fix to try before touching any code. (confidence: HIGH, source: multiple projects, date: 2026-03-09)
- **2-strike rule for CSS/layout bugs**: If 2 CSS fixes don't work, STOP guessing. Trace the full chain: what state changed → what component re-rendered → what DOM mounted/unmounted → what caused the layout shift. The bug is often in a parent component, not the element itself. (confidence: HIGH, source: multiple projects — 5 failed attempts before tracing to parent reflow, date: 2026-03-08)
- **Verify subagent claims before putting them in a plan**: Subagents occasionally misread patterns or flag correct API as bugs. When a subagent reports something as "critical" or "buggy", read the actual code lines before including it in the plan. Examples: LangGraph `ainvoke(None)` flagged as bug (correct API); reviewer subagent flagged RLS as missing without reading the migration SQL — it was already there. **Specific failure mode**: reviewer/research subagents don't automatically read adjacent files (migrations, schemas, config). A CRITICAL security flag from a subagent is only confirmed after checking the actual evidence file yourself. (confidence: HIGH, source: multiple projects — 3 sessions, date: 2026-03-09)
- **Search ALL injection points, not just the obvious one**: When modifying how data is processed, always grep for ALL places that code path is called. Easy to miss fallback paths and leave an optimization half-done. Pattern confirmed 3×: same issue for guidelines injection, RAG config params, and retriever call sites. (confidence: HIGH, source: multiple projects — 3 sessions, date: 2026-03-11)
- **`if x:` truthiness guard silently skips falsy-but-valid values**: Empty string `""`, `0`, and `False` are all falsy but can be valid IDs/values. Use `if x is not None:` when guarding on presence, not `if x:`. Example: `if node_ids and session_id:` skipped detection when `session_id=""`. (confidence: HIGH, source: multiple projects — 2 variants, date: 2026-03-09)
- **`URLSearchParams.size` is unreliable across Node versions**: `.size` getter was added in Node 19 — not available in Node 18 or earlier. Even Node 20 environments (e.g. Docker alpine) can behave unexpectedly. Always use `params.toString()` truthiness (`const qs = params.toString(); url + (qs ? '?' + qs : '')`) instead of `params.size`. (confidence: HIGH, source: confirmed — caused runtime 500, date: 2026-03-14)
- **Restart dev servers after ANY code change before declaring done**: Both Next.js (Turbopack) and Go (`go run .`) require manual restart to pick up new files/routes. Turbopack may not detect newly created page directories — returns 500. Go binary never hot-reloads — new routes return 404 until restart. **BLOCKING**: After implementing backend/frontend changes, always (1) restart affected server, (2) verify the new endpoint/page responds with curl, (3) THEN tell user to test. Kill first: `kill $(lsof -ti :PORT)`. Known triggers: new file created while dev server runs, new route added to Go mux, `npm run build` while Turbopack runs. (confidence: CRITICAL, source: confirmed — 7 occurrences across 4 sessions on a Go + Next.js project, date: 2026-03-14)
- **CORS `ERR_FAILED` + "no headers" = backend crashed before sending response**: When a CORS error shows no response headers (not even a 500), the issue is NOT CORS misconfiguration — it's a backend crash. Starlette's CORSMiddleware doesn't add CORS headers when inner middleware raises an unhandled exception. Diagnosis: (1) OPTIONS preflight succeeds → CORS config is fine; (2) actual POST/GET fails with ERR_FAILED → crash in handler. Fix: find the AttributeError/crash in backend logs, not the CORS config. (confidence: HIGH, source: multiple projects, date: 2026-03-09)
- **Fix attribute chain errors by reading the class definition first**: When `obj.foo.bar` raises AttributeError, read the class at its definition (not callers) to find the real attribute name. Guessing one level at a time wastes cycles. (confidence: HIGH, source: multiple projects — 2 rounds of guessing before reading class, date: 2026-03-09)
- **Reproduce the user's exact reported scenario before declaring a fix**: When a user reports a bug in a specific path (authenticated route, specific URL, specific stateful interaction), do NOT declare success after testing only the easy/default/guest path. Common failure mode: 1) make change, 2) reload as guest / default state, 3) "looks fixed!", 4) user reports "still broken", 5) realize the actual reported scenario was never tested — there's a second, deeper bug only visible on the reported path. Cost: 2+ extra cycles and credibility hit. Discipline: before claiming a fix, write out the user's exact reproduction (URL + auth state + interaction sequence) and walk through each step specifically. Two distinct projects have hit the same shape: (a) CSP fix verified on guest path missed the authenticated bug; (b) auto-save hook wired but never actually triggered in the real UI flow. Adjacent to the "verify trigger path end-to-end" rule for hooks. (confidence: HIGH, source: confirmed across 2 projects, date: 2026-05-07)
- **Missing API calls in the network tab reveal which gate is blocking**: When debugging stuck UI (spinner, missing list, half-rendered section), enumerate the API calls the code SHOULD make (read the component + its loader functions), then diff against the network tab's actual calls. The endpoint that's missing reveals the call-site that didn't fire — usually a guard, conditional, or effect that returned early. Faster than instrumenting components with logs because it works at the boundary, not inside the render tree. Especially effective when the symptom is "nothing visible happened" — the absence of an HTTP request is louder than the absence of a console log. (confidence: MED, source: 1 project but generic technique, date: 2026-05-07)

## Architecture

- **Global-first design**: Build frameworks in `~/.claude/` (applies everywhere), then scaffold project-specific layers via `/init-env`. Avoid project-only solutions when the pattern is reusable. (confidence: HIGH, source: multiple projects, date: 2026-03-08)
- **PostgreSQL CHECK constraint modification = DROP + re-ADD**: CHECK constraints cannot be ALTERed in-place. To add a new allowed value: `ALTER TABLE t DROP CONSTRAINT t_col_check; ALTER TABLE t ADD CONSTRAINT t_col_check CHECK (col IN ('old1', 'old2', 'new'));`. Same for removing values. Always pair with a down migration that reverts the constraint. (confidence: HIGH, source: confirmed across 3 sessions, date: 2026-03-14)
- **3-layer "one active per user" enforcement**: Never rely on just one layer. Enforce at: (1) application logic (check in handler before insert), (2) DB partial unique index (`CREATE UNIQUE INDEX ... WHERE status IN ('pending','approved')`), (3) frontend pre-fetch + hide CTA proactively. Each layer catches a different failure mode: app logic catches normal flow; DB index catches race conditions and direct API calls; frontend hides the affordance so users never hit the constraint at all. (confidence: HIGH, source: confirmed, date: 2026-03-14)
- **Partial unique index for "one active per user" with history**: `CREATE UNIQUE INDEX idx_foo_user_active ON foo(user_id) WHERE status IN ('pending','approved')`. Enforces one active record per user while allowing unlimited rejected/cancelled/historical records. Much more flexible than a simple UNIQUE constraint on `(user_id)`. (confidence: HIGH, source: confirmed, date: 2026-03-14)
- **setLive/commitLive split for editor undo history**: Any reactive editor with sliders + undo must separate continuous input from history commits. `setLive(params)` during drag = live preview, no history entry. `commitLive()` on drag end = one undo step. `update(params)` for discrete actions (preset apply, AI apply, reset button) = immediate history entry. Without this split, undo steps back one slider tick — visually invisible. Apply to ALL input panels, not just one. (confidence: HIGH, source: iOS photo editing app — undo/redo fix, date: 2026-03-12)
- **For a retry/loop/spawn/auto-recovery engine, the safety mechanism IS the MVP — never slice it off the first cut**: backoff, a circuit-breaker (give-up-after-K), and a hard budget are NOT "hardening" to defer to a later slice. Without them the "minimal first slice" is a hammer — a reclassify-and-retry with only a fixed delay = dozens of respawns per minute on a sustained error (the exact API-hammering / runaway the engine exists to prevent). The first SHIPPABLE cut of such an engine must include all of: (1) exponential backoff before each retry; (2) a circuit-breaker tied to a PROGRESS signal (bail/park after K attempts that make no verified progress, so a wedged item stops fast); (3) a hard budget — wall-clock OR turn/attempt count, env-tunable, that even "made progress" cannot reset — as the unattended-cost backstop; (4) a dedupe/idempotency gate so the retry path and any manual/other path can't double-fire on one item. A scoping review that calls these "later slices" is mis-slicing — flag it before building. (confidence: HIGH, source: 1 project, date: 2026-06-29)

## Claude Code Skills

- **Executable slash command requires `SKILL.md` in a subdirectory**: A flat `~/.claude/skills/foo.md` is a role persona (loaded as instructions, not invocable). An executable `/foo` command requires `~/.claude/skills/foo/SKILL.md` — the subdirectory signals it's a slash command. These two look similar but behave completely differently; confusing them means the command silently never appears. (confidence: HIGH, source: discovered when a custom skill wasn't invocable, date: 2026-03-31)
- **Project skill overrides global skill via `.claude/skills/`**: `<project>/.claude/skills/<name>/SKILL.md` takes precedence over `~/.claude/skills/<name>/SKILL.md`. Use this for project-specific domain expert configuration — keep the global version language-agnostic, scaffold the project override with `/init-env`. Enables one workflow to serve all projects without forking the global file. (confidence: HIGH, source: confirmed when overriding rplan-review for a Go/Next.js/PostgreSQL project, date: 2026-03-31)
- **Parallel domain expert agents > sequential generalist probe loop for plan review**: A single generalist asking probe questions sequentially requires 5-10 manual prompt rounds to cover all risk areas. Launching domain-specific agents in parallel (Backend, Frontend, DB/Security, Product) covers all blind spots in one pass — each agent knows its domain's failure modes and non-negotiable blockers. The synthesis step deduplicates and scores confidence automatically. Apply this pattern to any review or audit skill that currently uses a sequential loop. (confidence: HIGH, source: rplan-review redesign — extends "confidence-driven loops" pattern, date: 2026-03-31)
- **QA skills must be criteria-driven, not tool-driven**: A QA skill that runs `go test`, `npm test`, and `playwright test` generically fails silently when any tool is missing or not set up — it ends with "install X" instead of useful signal. The correct design: read the plan's Success Criteria, classify each criterion by type (API/test/file/UI), and run the best available command for that type. `curl` covers API criteria without a test framework; `go test -run [Name]` covers service criteria; file checks cover migration criteria. Generic tool commands are a fallback, not the primary driver. (confidence: HIGH, source: /qa failure mode — caught in practice, date: 2026-03-31)
- **Review skills must rewrite vague criteria, not just flag them**: A review phase that flags "acceptance criteria too vague" as a blocker forces the user to fix manually — this is the same friction being automated away. The correct design: rewrite each vague criterion in-place using the plan's wiring (Given/When/Then + exact test command + expected outcome), edit the plan file, and proceed. By the time implementation starts, every criterion must be machine-executable. "Flag and block" is half the job; rewriting completes it. (confidence: HIGH, source: rplan-review Phase 1.5 design, date: 2026-03-31)
- **MANUAL and BLOCKED are not SKIP**: In QA and review skills, a criterion that can't be auto-verified still needs a result. `MANUAL` = UI interaction required — list the exact browser steps. `BLOCKED` = dependency missing (server down, token needed) — state exactly how to unblock. `SKIP` means "we gave up" and produces a false green signal. Every criterion must have a verdict; none may be silently omitted. (confidence: HIGH, source: /qa design correction, date: 2026-03-31)

- **Lean CLAUDE.md (<100 lines) with @imports**: Long CLAUDE.md gets ignored as context fills. Keep root file lean, use @imports for details (execution-protocol.md, plan-template.md, project-context.md). (confidence: HIGH, source: multiple projects + external sources, date: 2026-03-08)
- **Three-file settings separation**: `.claude/settings.json` (committable project hooks), `.claude/settings.local.json` (gitignored personal permissions), `~/.claude/settings.json` (global hooks). Never mix concerns across these files. (confidence: HIGH, source: multiple projects + Claude Code docs, date: 2026-03-08)
- **Feature-flag via empty env var (`key == "" → no-op`)**: Instead of boolean `if cfg.FeatureEnabled` flags, check `if apiKey == ""` (Go) or `if not api_key` (Python). The service constructor accepts the key and no-ops gracefully when empty. Confirmed across 3 projects with optional third-party integrations (payment, messaging, vision APIs). Zero config overhead for optional integrations. (confidence: HIGH, source: confirmed across 3 projects, date: 2026-03-14)
- **Skill design: use confidence-driven loops, not fixed iteration counts**: Skills that probe, review, or retry should loop until a goal condition is met (confidence >94%, success flag, etc.) rather than running a fixed N times. Fixed counts either waste time (when goal is reached early) or stop too early (when more probing is needed). Applies to: `/rplan-review` (probing rounds), retry loops, validation passes. (confidence: HIGH, source: confirmed — 2 corrections in one session, date: 2026-03-14)
- **Background Bash tasks need `bash -c` wrapper**: `cd /path && command` in background mode doesn't persist cwd — the `cd` runs in one shell, the command in another. Use `bash -c 'cd /path && command'` for reliable execution. (confidence: HIGH, source: multiple projects — failed 6+ times across 2 sessions, date: 2026-03-08)
- **Bash tool foreground cwd persists across calls — explicit `cd` to root before git ops**: Opposite behavior to background mode. The Bash tool's cwd persists between sequential FOREGROUND calls within a single Claude Code session (env vars don't, but cwd does). After an explicit `cd backend` (or any subdirectory `cd`), all subsequent Bash calls run from there until you reset. Failure mode: `git diff <relative-file-path>` returns EMPTY silently because the relative path resolves to e.g. `backend/<file>` which doesn't exist; git reports "no path matches" rather than "wrong directory". Looks like "no changes" — wastes diagnostic time. Mitigations: (1) explicit `cd <project-root>` at the start of any git-heavy block; (2) use absolute paths in `git diff` / `git status` arguments; (3) `pwd` first when output looks suspiciously empty. **Multi-repo / parallel facet:** in a workspace with sibling repos, multiple Bash calls issued in ONE message all inherit (and race on) the same persisted cwd — a call without its own explicit `cd` runs in whatever directory a concurrent/previous call left behind (real failure: one repo's `git log` silently printed a sibling repo's history, looked like duplicate commits). Give every parallel/multi-repo call its own `cd <abs-path> && …` or use `git -C <dir>`; never rely on inherited cwd when commands run concurrently or span repos. (confidence: HIGH, source: confirmed across 2 projects, date: 2026-05-22)
- **Newly-created (never-staged) files: `mv dest/ && git add dest/file` — NOT `git add src && git mv src dest`**: `git mv` requires the source file to already be tracked. For files created in the current session and never committed (e.g. plan files, context files), `git mv` fails with "not under version control" even after `git add`. The only working pattern: `mv file dest/ && git add dest/file && git commit`. Earlier lesson "`git add` before `git mv`" only applies to files that were previously tracked. (confidence: HIGH, source: 1 project — hit this twice in the same session, date: 2026-05-22)
- **`npm run <cmd>` in background Bash tasks fails when RTK is active**: RTK intercepts `npm run` and rewrites the command, which breaks in background/subshell contexts. Use direct binary paths instead: `node_modules/.bin/next dev`, `node_modules/.bin/vite`, etc. (confidence: HIGH, source: confirmed — 2× in background dev-server tasks, date: 2026-03-09)
- **`rtk` rewrites `cat | jq` pipes AND inflates `wc -l` counts**: (1) Value substitution: RTK intercepts `cat`/`head`/`tail` and substitutes a type-summary schema (e.g. `{field: string, n: number}`) for actual values — `jq` fails with "Invalid numeric literal" because it received a YAML-ish schema. Workaround: `rtk proxy curl … > /tmp/x.json` then `jq '.foo' /tmp/x.json`. (2) Line count inflation: RTK decorates grep/search output with file headers, blank lines, and match-count labels. `grep … | wc -l` reports 4–6× the actual match count. Never trust `wc -l` on piped RTK output — read the RTK formatted match count directly (shown in brackets) or use `grep -c pattern file` (no pipe). (3) Guardrail false-positives: the same decoration breaks boolean guards like `cmd | grep -q .` — an injected decoration/`ok` line makes `grep -q .` match even when the command's REAL output is empty (real failure: `git status --porcelain src/core/ | grep -q . && echo "CORE TOUCHED"` fired despite `src/core` being untouched). Never gate logic on `grep -q .` of piped output; match a specific token (`… | grep -c '<path>'`, expect 0) or write to a file and test that. For Playwright JSON, see the `PLAYWRIGHT_JSON_OUTPUT_NAME` entry below. (confidence: HIGH, source: confirmed across 5 sessions, date: 2026-05-19 → 2026-05-24)
- **`git add` requires single-line space-separated args**: Backslash line continuation in Bash tool fails with "pathspec ' '" error — shell interprets each line as a separate command. Always: `git add file1 file2 file3` on one line. (confidence: HIGH, source: multiple projects — 2 sessions, date: 2026-03-09)
- **`.env` files need `export` for child processes**: `source .env` sets vars in the current shell but doesn't export them — `os.Getenv` (Go), `process.env` (Node), `os.environ` (Python) all see empty values. Use `export $(grep -v '^#' .env | xargs)` before `go run .` / `node .` to make vars available to child processes. (confidence: HIGH, source: confirmed — caused OAuth "Missing client_id" error in production, date: 2026-03-14)
- **Symlink pattern for portable `~/.claude/` config**: Create a git repo (`~/claude-config/`) containing skills/, docs/, memory/, hooks/, CLAUDE.md. Symlink `~/.claude/` dirs to the repo. Tools write through symlinks → changes land in the repo. Run `sync.sh` after `/reflect` to commit and push updated learnings. New machine setup: `git clone + ./install.sh`. (confidence: HIGH, source: implemented and verified, date: 2026-03-11)
- **Fix CI / work a second branch via a throwaway worktree when the repo checkout is occupied**: When a single-checkout repo is sitting on in-flight work you must not disturb (uncommitted WIP, or a disposable integration branch) and you need to fix a *different* branch, do NOT switch the shared checkout's branch out from under it. Instead: `git worktree add /tmp/<x> origin/<branch>` (use `--detach origin/<branch>` if that branch is already checked out elsewhere — git blocks a duplicate branch checkout but allows detached), symlink the main checkout's deps into it (`ln -sfn <repo>/node_modules /tmp/<x>/node_modules` — read-only for tsc/eslint/jest, so safe and instant vs a fresh install), run the real lint/typecheck/test, commit, push; then `rm` the symlink BEFORE `git worktree remove --force` (so cleanup doesn't follow it into the real tree). Keeps the workspace at its normal folder count and never collides with the occupied checkout. **Companion triage:** a `cannot find module` tsc error under the SYMLINKED deps is a FALSE POSITIVE if the dep is declared in that branch's `package.json` (the borrowed tree just lacks it; CI `npm ci` resolves it) — confirm with `npm i --no-save <dep>` then re-typecheck. Distinguish npm-package imports (install artifact, ignore) from relative/alias imports of local source files (`../hooks/x`, `@modules/...` → real missing file / cross-branch leak). (confidence: MED, source: 1 project — 2 repos same session; generalizes the "/tmp sandbox + stubbed git" Workflow entry, date: 2026-05-25)
- **Verify "what's on `main`" against `origin/<branch>` after a fresh `fetch` — never trust the local checkout or the board**: In multi-machine / multi-agent / active-remote repos (another machine or an `[auto]` bot pushes constantly), both the local checkout AND any roadmap/status board lag reality. Recurring footguns: planning a slice against a dependency that actually lives only on a feature branch (grep it at `origin/main` first); calling an epic "not started" when it's already merged (`git log --merges origin/main | grep <epic>` + confirm the deliverable files exist); `add-epic`/new-ID on a stale base colliding with IDs the team already claimed (`git ls-tree -r --name-only origin/main | grep -oE 'E[0-9]+'` for the true next-free). **Push-race recovery:** on a rejected push, first inspect the incoming commit's touched files. For the CANONICAL repo where your commits are new and others' edits sit in different files → `git pull --rebase && push` (rebase only when there's no file overlap). For READ-ONLY synced/generated copies → `fetch → reset --hard origin/main → regenerate → commit → push` (beats rebase, which hits whole-file conflicts on generated content). **Never force-push `main`** (usually remote-protected anyway). **Conflict-marker hygiene (bit me 2×):** after ANY rebase/merge conflict resolution, `grep -rnE '^(<{7}|={7}|>{7})'` EVERY touched file before `git add`/`rebase --continue` — a truncated (`| tail`) rebase/push output hides which files conflicted, so resolving only the named file and blind-`git add`-ing the rest commits live `<<<<<<<` markers. Likewise never `git add -A`/`git add .` in a shared meta-repo (it sweeps in other people's untracked drafts) — stage explicit paths. (confidence: HIGH, source: confirmed across 4 projects + many sessions, date: 2026-05-25 → 2026-06-03)
- **Even an EXPLICIT-path `git add` captures a concurrent session's uncommitted edits in that file** — "stage explicit paths" is necessary but NOT sufficient when another agent/session edits the SAME working tree (no git remote required). `git add foo.ts` stages foo.ts's WHOLE diff vs HEAD, including hunks you didn't write. Real failure: a "focused fix" commit swept in another session's in-flight feature whose code `import`ed an UNTRACKED module → the resulting HEAD failed to build standalone, while the working-tree `tsc` still passed (consumer + producer both present, uncommitted, in the tree). Mitigations, cheapest first: (1) read the session-start `git status` snapshot — any file already `M` (or belonging to an in-flight feature) is entangled BEFORE you touch it; (2) `git diff --cached <file>` before committing and confirm ONLY your hunks are staged; (3) verify **HEAD itself**, not the working tree, in a throwaway detached worktree (`git worktree add --detach /tmp/x HEAD` + symlink `node_modules` + per-workspace `tsc`/test) — only this catches a feature split across the commit boundary; (4) clean-tip recovery: if your commits are the only ones on a known-good base, `git reset --mixed <base>` (zero file changes) then commit only the cleanly self-contained files and leave the entangled blob for its owner. (confidence: HIGH, source: confirmed 2× on same project — concurrent same-tree editing, date: 2026-06-27)
