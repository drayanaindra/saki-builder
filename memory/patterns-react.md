# React / Frontend Patterns

Stack-specific patterns for React, Next.js App Router, Vite, and TypeScript/Jest. Loaded on-demand via `@import` in project CLAUDE.md files that use this stack.

## Build / Dependencies

- **Vite 8 (rolldown) requires `import type` for all MUI type re-exports**: Vite 8 switched to rolldown bundler. Combined `import X, { XProps } from '@mui/material/X'` syntax causes `[MISSING_EXPORT]` build errors for any type-only export from MUI subpath imports. Fix: split into `import X from '@mui/material/X'` + `import type { XProps } from '@mui/material/X'`. Also applies to `SxProps`, `Theme` from `@mui/material/styles`. This is a Vite 8 / rolldown issue only — Vite 5 worked fine. (confidence: HIGH, source: ANA design system build, date: 2026-04-14)
- **MUI v5 + npm = pin icon version explicitly**: `npm install @mui/icons-material` auto-resolves to v9 even when `@mui/material` is v5, causing icon export path incompatibilities. Always pin: `npm install @mui/icons-material@5`. (confidence: HIGH, source: ANA design system build, date: 2026-04-14)

## CI / Quality Gates (TypeScript / Node)

- **`--testPathPatterns` (plural) is required in this Jest version — singular triggers deprecation**: The edbot-be and edbot-fe repos use a Jest version where `--testPathPattern` (singular) emits a deprecation warning and may not filter correctly. Always use `--testPathPatterns` (plural), or use `npx jest "<pattern>"` as a positional arg. This has appeared 3+ times in edbot sessions — treat as a hard rule, not a style preference. (confidence: HIGH, source: edbot-workspace-3 — confirmed 3+ sessions, date: 2026-05-28)
- **Run the repo's full CI-equivalent gates locally before raising an MR — module tests alone prove nothing about the pipeline**: CI typically stacks gates that module/unit test runs never touch: repo-wide lint with strict rule sets (`typedef` annotations, i18n no-literal-string at error level, import/order), `npm ci` lockfile integrity, and a static-analysis quality gate on NEW code only (cognitive complexity, no-void, no-nested-ternary, readonly props). Before raising an MR run, at minimum: full `lint` script (not eslint on changed files with default config), full typecheck, full test suite, and — where a sonar-style gate exists — eyeball the diff for new-code smells the gate counts. Each missed gate costs a push-fail-diagnose-push round-trip on a shared pipeline. (confidence: HIGH, source: confirmed across 2 projects / 4+ sessions, date: 2026-06-06)
- **SonarQube new-code gate failure — pin the violation, never retry blind**: When a CI SonarQube quality gate fails on `new_violations > 0`: (1) a feature branch's gate is measured against the project's `PREVIOUS_VERSION` baseline (last release tag), so EVERY commit merged into `main` since that tag counts as "new code" on your branch — the flagged issue may be in `main`'s code, not your diff. (2) If the CI analyzes all branches into ONE project key (no `sonar.branch`/`sonar.pullrequest` param — check the trace for `dashboard?id=<key>` with no branch), concurrent pipelines clobber each other's analysis, so `inNewCodePeriod=true` and my-files filter queries read **0 transiently**. To pin the exact offender reliably, query `GET /api/issues/search?componentKeys=<key>&createdAfter=<the gate's PREVIOUS_VERSION date>&resolved=false` (the date is in the gate's `Full response` JSON `period.date`). A blind job-retry **deterministically re-fails** (same baseline). Note: a pre-existing rule (e.g. `typescript:S6759` readonly-props) re-fires when you merely MODIFY a component's signature — the touched line becomes "new code". (confidence: HIGH, source: edbot — confirmed 3+ sessions, date: 2026-06-01)
- **`node_modules` as a git-tracked symlink silently breaks npm/jest across checkouts**: In repos where `node_modules` is a symlink (and/or tracked), recurring traps: (a) `.gitignore` `node_modules/` (trailing slash) only ignores DIRECTORIES — a symlink named `node_modules` stays tracked (mode `120000`); add a bare `node_modules` entry too. (b) A committed symlink-deletion (`D node_modules`) replays during `git rebase` and wipes the real directory — run `npm install` after rebasing such a branch. (c) A broken/circular symlink makes `jest` exit 194 with no output, or "Preset not found" — diagnose with `npm ls jest` / `ls node_modules/ts-jest`, fix with `rm node_modules && npm install`. Always verify `node_modules` health after any branch switch / rebase / stash-pop before debugging test failures. (confidence: HIGH, source: edbot — confirmed 3+ sessions, date: 2026-06-01)

## Jest / Testing

- **jest.mock factory hoisting TDZ trap**: `jest.mock(module, () => ({ fn: myVar }))` where `myVar` is a `const` declared in the same file will throw `ReferenceError: Cannot access 'myVar' before initialization` — jest.mock calls are hoisted to the top of the file before any variable declarations run. Fix: use `jest.fn()` inline inside the factory at file top, then derive the reference below via `const mockFn = (jest.requireMock(module) as { fn: jest.Mock }).fn`. Affects any file where the mock factory references a module-level variable. (confidence: HIGH, source: edbot-be, date: 2026-05-27)
- **`jest.mock()` inside `it()` body is a no-op**: babel-jest hoists ALL `jest.mock()` calls to module-load time regardless of where they appear in the source file. A `jest.mock(...)` call inside an `it()` body executes "later" syntactically but actually has already been hoisted and won't replace the module again at runtime. The module is wired once — at file load — and calling `jest.mock()` inside a test does nothing. Fix: always declare `jest.mock('@/module/name', factory)` at module level (top of file), then per-test overrides go through `(importedFn as jest.Mock).mockResolvedValueOnce(...)`. (confidence: HIGH, source: edbot-be E263, date: 2026-06-16)
- **`jest.clearAllMocks()` keeps mock implementations — only `jest.resetAllMocks()` removes them**: `clearAllMocks()` resets call history and instances but PRESERVES `mockReturnValue`/`mockResolvedValue`/`mockRejectedValue` implementations. A persistent mock from one `describe` block leaks into later ones in the same file. A "passing" test may depend on an earlier `describe`'s leaked rejection; adding a new `describe` that sets a conflicting persistent mock flips the leak and breaks downstream tests. Fix: use `mockResolvedValueOnce()`/`mockRejectedValueOnce()` for per-test overrides, and call `jest.resetAllMocks()` (not `clearAllMocks`) in `beforeEach` when isolation between describes is needed. (confidence: HIGH, source: confirmed across 2 projects, date: 2026-06-06)
- **Integration tests go stale when service transport changes**: When a service moves from HTTP → event bus (or vice versa), integration tests that spy on `fetch`/`axios` keep passing locally (mock is set up but never consumed) but timeout in CI if the new transport triggers a real external call (e.g. DB via eventBus persister). Always search for and update integration tests alongside transport-layer changes. (confidence: HIGH, source: edbot-be, date: 2026-05-27)
- **Playwright e2e auth: the app can WIPE your injected token on init — seed the guard's precondition, and prefer globalSetup+storageState**: Setting `access_token`/`refresh_token` via per-test `addInitScript` is silently undone when the app runs an init-time session reset (cookie/version migration, `localStorage.clear()` on mount, token-gated reset) that fresh Playwright contexts always trigger (empty localStorage). Symptom = a WHOLE auth-gated suite failing with selector/`toBeVisible` TIMEOUTS (not assertion mismatches), and the QA/e2e phase ballooning to 30–60 min of retry loops. Real case: `migrateCookiesIfNeeded()` cleared tokens unless `localStorage.cookie_migration_v1` was set. Fix: (1) grep the app for the init guard (`migrat|cookie_migration|localStorage.(clear|removeItem)|remove.*token`) and seed its PRECONDITION flag alongside the token; (2) prefer authenticating ONCE in `globalSetup` and persisting full storage via `use.storageState` (portable mechanism; only login call + storage keys differ per app) over per-test injection. (confidence: HIGH, source: 1 project — cost 50+ min in a /build QA phase; mechanism is generic, date: 2026-06-27)
- **Node 22+/26 ship a native `localStorage` global (gated behind `--localstorage-file`) that throws and SHADOWS jsdom's under Vitest**: any test touching `localStorage` (a persistence layer, a store hook) fails with `localStorage is not available because --localstorage-file was not provided`, and a `localStorage.clear()` in `afterEach` then nukes EVERY test in the file — including pure non-DOM ones. **Tell:** pure tests with no DOM/storage also failing → the fault is global setup, not your logic. Fix: install a deterministic in-memory shim in the Vitest `setupFiles`, don't trust jsdom to provide it: `Object.defineProperty(globalThis, 'localStorage', { value: new MemoryStorage(), configurable: true, writable: true })` where `MemoryStorage` is a `Map`-backed `Storage` impl. (confidence: HIGH, source: 1 project, date: 2026-07-01)

## React Patterns

- **Array data from APIs/props must be null-guarded with `?? []` or `= []`**: Go nil slices serialize to JSON `null` (not `[]`). Any other backend that returns `null` for empty arrays causes `TypeError: Cannot read properties of null (reading 'length')` or `Cannot read properties of undefined (reading 'map')`. Defense: (1) on API response: `setItems(data ?? [])`, (2) on component props: `items: Item[] = []`. Apply to ALL `setState` calls that receive array data from fetch responses, and ALL array props with no guaranteed parent value. Real impact: 8 dashboard pages crashed simultaneously from one null array. (confidence: HIGH, source: confirmed across 2 projects — 3+ sessions, date: 2026-03-28)
- **Lucide icon names: verify before use** — compound/descriptive names like `LayoutPanelRight`, `PanelLayoutRight` do not exist. Real names are short: `PanelLeft`, `PanelRight`, `PanelTop`, `PanelBottom`. Verify with: `node -e "const l = require('./node_modules/lucide-react'); console.log(!!l.PanelRight)"`. (confidence: HIGH, source: multiple projects — 2 separate sessions, date: 2026-03-10)
- **Optional `className` for flexible-width components**: When a component has a hardcoded width (e.g. `w-[400px]`), add `className?: string` prop and use `className ?? 'w-[400px] ...'` as the root element's class. Existing consumers are unaffected; callers that need full-width or overlay can override freely. (confidence: MED, source: multiple projects, date: 2026-03-10)
- **Grep ALL usages of any symbol before removing it**: Before deleting a state variable, import, prop, or exported function, grep the ENTIRE file (or codebase) for all references — including setters (`setFoo`), secondary uses of the same import, and downstream consumers. Confirmed causes: `MapPin is not defined` (import removal, 2×), `Search is not defined` (import removal), stale setter crash. Use: `grep -n "symbolName" file.tsx` before any deletion. (confidence: HIGH, source: multiple projects — 6+ occurrences across several projects, date: 2026-03-09)
- **Ref-for-latest-value in async callbacks**: When a callback closed over state will be called asynchronously (WS `onmessage`, MediaRecorder `onstop`, `setTimeout`, audio `onended`), use a ref (`valueRef.current = value`) synced in the render body so the callback always reads the current value. State is stale inside closures; refs are not. (confidence: HIGH, source: multiple projects — voice + WebSocket handlers, date: 2026-03-09)
- **Recursive async hook restart needs a function ref**: For hooks that restart themselves (continuous recording, polling loops), store `startFnRef.current = startFn` after `useCallback`, then call `startFnRef.current()` inside async callbacks (`onstop`, `onended`). Calling the function directly from inside its own closure causes a stale reference to the initial version. (confidence: HIGH, source: multiple projects, date: 2026-03-09)
- **Two restart sites for continuous audio/voice loops**: Auto-restart after a successful round goes in `audio.onended`. Auto-restart after an empty/silent round must go in the `onstop` handler itself (with a shorter delay). Missing either site silently kills the loop. (confidence: HIGH, source: multiple projects, date: 2026-03-09)
- **`useSearchParams()` requires `<Suspense>` boundary in Next.js App Router**: Components using `useSearchParams()` must be wrapped in `<Suspense>` — build fails at static generation without it. Split into a client component (with `useSearchParams`) imported by a server component that wraps it in `<Suspense fallback={...}>`. (confidence: HIGH, source: confirmed across 2 projects, date: 2026-03-14)
- **React Context value-identity trap: `useSyncExternalStore` for external mutable stores**: `<Provider value={store}>` with a stable `store` reference (e.g. `useMemo(create, [])`) does NOT re-render consumers via Context alone — React's `Object.is` check skips because the value didn't change. Wiring the store's mutations to the Provider's `setState` doesn't help if the same store reference passes through. Fix: maintain a `version: number` on the store that increments on every `emit()`, expose `subscribe(cb)` and `getVersion()`, and consume via `useSyncExternalStore(store.subscribe, store.getVersion)` in the hook. This is the React-18 idiomatic pattern for external mutable stores. Plain `useReducer + useEffect(subscribe)` looks correct but only re-renders the Provider, not sibling consumers of the same Context. (confidence: HIGH, source: 1 project but applies to any React 18+ with mutable external store + Context, date: 2026-05-10)
- **Compound interactive row (select + secondary action): outer `<div>` + sibling `<button>` elements — no nested buttons**: HTML disallows `<button>` inside `<button>`. When an existing list row or chip `<button>` needs a second action (e.g. a delete ×), restructure as: outer `<div className="existing-class">` (inherits all CSS) + selection `<button style={{ flex: 1 }}>` + action `<button>`. Each button handles its own click; no `stopPropagation` needed. The div takes the background/border-radius styling via the existing CSS class. (confidence: HIGH, source: 1 project — applied identically in 2 components same session, date: 2026-05-22)
- **Serialize array props to strings in `useEffect` dep arrays to prevent reference-instability re-fetches**: React uses `Object.is` in dep comparison — a new array instance (e.g. from `preferences?.interestDomainKeys`) is always unequal even if the contents are identical, causing spurious effect re-runs. Fix: derive string deps outside the effect (`const domainKeysStr = keys?.join(",") ?? ""`), include the string in the dep array, and close over the raw array inside the effect body. Test verification pattern: (1) initial fetch settles, (2) rerender with new array reference but same content, (3) `waitFor(() => loading === false)` again, (4) assert call count still 1. If a bug exists, loading briefly becomes `true` then `false` — waitFor will catch the re-fetch. (confidence: HIGH, source: edbot-fe E263, date: 2026-06-16)
- **`useMutation.onSuccess`: read from pre-mutation state BEFORE calling `queryClient.invalidateQueries()`**: When `onSuccess` reads from component state (e.g. `userTags.find(tg => tg.id === id)`) to determine side-effects (e.g. which filter to reset), it correctly reads the old snapshot because `invalidateQueries` is async — the refetch hasn't fired yet when `onSuccess` runs. This ordering is intentional and correct, but looks like a bug to future readers. Always add a one-line comment: `// read from pre-mutation snapshot before invalidation triggers refetch`. (confidence: HIGH, source: 1 project — reviewer flagged it as potentially stale, date: 2026-05-22)
- **Destructive-action confirmation: never morph the trigger into Confirm at the same screen coordinates**: A single user gesture — mouse double-click OR Enter/Space held — fires twice. Click 1 morphs the button, click 2 lands on the (autoFocused) Confirm at the same `(x, y)`, silently bypassing confirmation. Whole point of the confirmation step is defeated. Place the *safe* action (Cancel) at the original trigger coordinates with `flex: 1` and `autoFocus`; the destructive Confirm must require deliberate cursor movement away from the original position. Verify with `document.elementFromPoint(originalCx, originalCy) === safe-action-id`. /rplan's User Role Coverage edge-case checklist for any destructive UI must enumerate BOTH "keydown spam (Enter/Space held)" AND "mouse double-click at trigger coords" as named cases — covering only one is incomplete. (confidence: HIGH, source: 1 project but generic UI-safety rule, date: 2026-05-10)
- **Zustand v5 `persist` `onRehydrateStorage`: never mutate `state` directly — go through `set()`**: Inside the rehydrate callback, `state.foo = bar` does NOT notify subscribers in zustand v5 (worked in v4; silently broken in v5). The persist middleware passes a snapshot-like reference; only `set()` or store actions that call `set()` internally trigger re-renders. Symptom: persisted state propagates *partially* — keys touched by other `set()` calls (e.g. a side-effect action's `set({ isLoading: true })`) become visible, but pure-mutated keys never reach React. Real-world manifestation: `isHydrated` stays `false` from the component's view → effects gated on it never fire → stuck spinners and `{isHydrated && ...}` ternaries collapsing to `null`. Same root cause can present as multiple unrelated visual bugs in different components — grep ALL subscribers of the suspect flag, don't fix one symptom in isolation. Fix: expose an internal action like `_markHydrated(...)` that calls `set({ ..., isHydrated: true })`, then `state._markHydrated(...)` from the rehydrate callback — the action is bound to the same `set` from `create()`, so subscribers fire. (confidence: HIGH, source: 1 project but applies to any zustand v5 + persist setup, date: 2026-05-07)
- **Don't derive a "loaded/ready" boolean from `error === null`**: during an in-flight fetch the error is still null but the data is still empty, so the flag is a false-positive and any action gated on it (validation, empty-state, enabling a button) misbehaves with empty data. Use an explicit `loaded` boolean set on resolve, or a tri-state `loading | loaded | error`. Caught by a reviewer when an `error===null` "taxonomy loaded" check let an early Save flag every valid item as "unknown" and block. (confidence: HIGH, source: edbot-panel E34 — reviewer find, date: 2026-05-27)
- **Integer-typed schema fields behind `<input type="number">`**: `Number(e.target.value)` yields floats (e.g. `70.5`) that pass client checks then fail server schema validation (`"type":"integer"` → 422). Round on input (`Math.round`). (confidence: HIGH, source: edbot-panel E34, date: 2026-05-27)

## Next.js App Router

- **Same-segment navigation does NOT remount client components**: Navigating between `/content/movie-a` → `/content/movie-b` (same `[slug]` route) keeps the component mounted. `params.slug` changes in-place; all `useState` persists. Any state that should reset between "pages" (e.g. resume position, scroll position, fetched data) must be explicitly reset via a `useEffect` that depends on the route param. (confidence: MED, source: content streaming project — resume playback bug, date: 2026-03-19)
- **Turbopack dev-server caches stale bundle content in three distinct symptom families**: (a) **Stale chunk execution** — Turbopack reuses the chunk URL after a content edit (the chunk name is path-based, not content-hashed); the browser's HTTP cache (and Playwright's HTTP cache) hold the old JS. Hard reload doesn't always bust it. Fix from a Playwright spec: `await page.route('**/*chunk_hash*', r => r.fetch({headers:{'Cache-Control':'no-cache'}}))` before navigation, or `fetch(url, {cache:'reload'})`. (b) **HMR misses newly-added exports** — adding a new method to a frequently-imported large file (60KB+ `services/api.ts` style) and the browser still throws `[exportedObject].newMethod is not a function`. The grep-confirmable code change exists; the bundle didn't pick it up. Fix: `touch <file>` to retrigger HMR + Cmd+Shift+R hard refresh; if still stale, kill `next dev` and restart (`.next` cache desync). (c) **Project-supplied `Cache-Control: immutable` on `/_next/static/:path*`** — a `headers()` rule in `next.config.ts` that sets `public, max-age=31536000, immutable` (common copy-paste from prod CDN guidance) applies to dev too. Combined with (a) — same chunk URL across recompiles — this freezes the running tab forever on the first bundle the browser ever fetched: `nohup npm run dev`, `rm -rf .next`, full restart, none of it makes the browser re-fetch. The dev server prints a warning: "Custom Cache-Control headers detected for the following routes: /_next/static/:path*". Fix: gate that header rule on `!isDev` and emit `no-store` (alone — `must-revalidate` is redundant when paired with `no-store`) in dev. Symptom-to-root-cause shortcut: stale execution → cache-bust the chunk; missing export → force HMR rebuild; **chunk never re-fetches despite `cache: 'no-store'`** → inspect `next.config.ts` `headers()` for an immutable rule. (confidence: HIGH, source: confirmed 3× on same project across 3 sessions, dates: 2026-04-19 + 2026-05-06 + 2026-05-24)
- **SSR `{!user && <X aria-…>}` gates with cookie-based auth cause un-patchable hydration mismatches in React 19 / Next 16**: When `useAuth()` reads the auth token from `document.cookie` (client-only), `user` is `null` during SSR and `truthy` after the first client mount. A conditional render like `{!user && <div aria-label="…">…</div>}` renders the element on the server but expects it gone on the client — React detects the **attribute-level mismatch** and emits `"A tree hydrated but some attributes of the server rendered HTML didn't match the client properties. This won't be patched up."`. The SSR markup stays in the DOM alongside the user-truthy branches. Diagnostic symptom: both `{user && A}` AND `{!user && B}` appear in the DOM simultaneously (logically impossible from current source) — exactly the signal that says "this is hydration, not stale bundle". Fix: gate with a `mounted` boolean (`const [mounted, setMounted] = useState(false); useEffect(() => setMounted(true), [])`) so SSR + first client render both produce nothing (`{mounted && !user && X}`), then post-mount the useEffect flips it and the gate evaluates against the resolved `user`. The pattern is already used in many codebases for the cart-badge counter `{mounted && totalItems > 0 && …}` — extend it to every `!user`/`user`-attribute-bearing conditional you add. (confidence: HIGH, source: 1 project but applies to any Next.js SSR + cookie/localStorage auth, date: 2026-05-24)
- **Next.js 15+ dev + Turbopack + React 19 require `'unsafe-eval'` in CSP `script-src`**: React's dev runtime uses `eval()` for HMR, source maps, and stack reconstruction. If the project ships its own CSP header (e.g. via `next.config.ts` `headers()`), missing `'unsafe-eval'` crashes the dev client mid-hydration on hard refresh — symptom is a cryptic "this page couldn't load" overlay AND the UI gets stuck in a half-mounted state (spinners that never resolve, conditionally-rendered sections that disappear). Console points right at it: `[ERROR] eval() is not supported in this environment...React requires eval() in development mode`. Production must NOT have unsafe-eval — gate via `process.env.NODE_ENV === 'development'` so the directive only applies to dev. Pre-existing CSP entries from a Next 14 era don't break — only Next 15+ + Turbopack + React 19 dev runtime triggers the eval requirement. (confidence: HIGH, source: 1 project but applies to any Next.js 15+ project shipping its own CSP, date: 2026-05-07)
- **URL params for unauthenticated users must be captured on a public route**: Any hook reading `?param=` from the URL for unauthenticated visitors must be placed on a route that `isPublicRoute()` returns `true` for. Auth guards that render `null` (not children) for unauthenticated users prevent any hook inside protected pages from ever mounting. Always verify the target page is in `public-routes.ts` (or equivalent) before placing capture logic there. (confidence: HIGH, source: edbot-workspace-3 E24 — QA caught the bug, date: 2026-05-28)
- **`useSearchParams()` from next/navigation is unreliable in Next.js static-export mode**: In `output: "export"` + `next start` (production), `useSearchParams()` inside a Suspense boundary may resolve to empty even when search params are present. Prefer `window.location.search` + `new URLSearchParams(...)` in a `useEffect(() => {...}, [])` — no Suspense required, works in dev, production, and static-export modes. (confidence: HIGH, source: edbot-workspace-3 E24 — Playwright caught the bug, date: 2026-05-28)

## React / Frontend Architecture

- **Three-way render gate for async-resolved content**: When a component renders differently based on async state, use three branches: `null → Skeleton`, `resolved + data → Component`, `resolved + no-data → Fallback`. Never use a flat AND gate (`resolved && data ? <X> : <Fallback>`) — this incorrectly shows the fallback during loading. Template: `{state === null ? <Skeleton /> : data ? <Component /> : <Fallback />}`. (confidence: MED, source: content streaming project — resume playback, date: 2026-03-19)
- **Auth `isLoading` race — `isAuthenticated` starts `false` during token refresh**: Any `useEffect` that branches on `isAuthenticated` must also gate on `!isLoading` (or `!authLoading`). On mount, `isAuthenticated=false` AND `isLoading=true` — this is "unknown", not "logged out". If the effect fires before `refreshToken()` resolves, it executes the anonymous branch for every authenticated user. Guard: `if (isLoading) return;` as the first line in any auth-dependent effect. (confidence: MED, source: content streaming project — auth race during playback resume, date: 2026-03-19)
- **Callback/render props to avoid cross-feature imports**: When Feature A needs to render or interact with Feature B, use render props (`actionSlot?: React.ReactNode`) or callback props (`onTimeUpdate?: (currentTime, duration) => void`) instead of direct imports. The parent in `app/` orchestrates — it passes Feature B's component via prop to Feature A, which renders it without importing. Keeps features decoupled and independently testable. (confidence: HIGH, source: confirmed — 3 occurrences in one project (watchlist button, video player, content card), date: 2026-03-19)

## Vite

- **Vite dev module graph can serve a stale source file even after `npm run build` succeeds**: A long-lived browser tab can hold the old module while the dist build is up-to-date. Symptom: new `data-testid` attributes ARE queryable in the DOM (so partial HMR happened) but new state-machine behaviour doesn't fire. Hard-navigate with a fresh query-string (`?_t=cachebust`) — this forces a full re-fetch. When MCP-driven QA shows behaviour inconsistent with the source code, hard-navigate with `?_t=...` *before* assuming a real bug. Mirrors the Turbopack stale-chunk pattern. (confidence: HIGH, source: 1 project but applies to any Vite + long-lived browser/MCP tab, date: 2026-05-10)

## CSS / Tailwind

- **Never use `transition-all` on interactive cards/toggles**: Use `transition-colors` or list specific properties. `transition-all` animates width/height/shadow changes causing layout jank, especially in grid layouts. (confidence: HIGH, source: multiple projects, date: 2026-03-08)
- **Tailwind `focus:ring-offset-*` adds real box space**: Avoid on elements inside constrained grids/flexbox — it pushes parent containers wider on focus. Use `focus:ring` without offset, or `focus:outline` instead. (confidence: MED, source: multiple projects, date: 2026-03-08)
- **`getComputedStyle` > screenshots for visual-parity / refactor verification**: When verifying a CSS refactor (especially one that drops style declarations on an outer wrapper), assert with `getComputedStyle(el).getPropertyValue('background-color')` etc. — NOT screenshots. Cream-on-white bg, dark-brown vs pure-black text, 13px vs 16px are near-indistinguishable in PNGs at typical zoom; computed-style strings are exact. Screenshots are supplementary, not load-bearing. Before deleting an outer-wrapper style declaration, grep `body`/`global.css` to check whether the property is declared at root — children typically inherit from `body`, which falls back to browser defaults (white bg, black text, 16px) if not set. (confidence: HIGH, source: confirmed 2× on same project, date: 2026-05-08 → 2026-05-09)
- **`URLSearchParams.size` is unreliable across Node versions**: `.size` getter was added in Node 19 — not available in Node 18 or earlier. Even Node 20 environments (e.g. Docker alpine) can behave unexpectedly. Always use `params.toString()` truthiness (`const qs = params.toString(); url + (qs ? '?' + qs : '')`) instead of `params.size`. (confidence: HIGH, source: confirmed — caused runtime 500, date: 2026-03-14)
- **A desktop CSS grid that collapses to one column on mobile leaves a big empty band between chrome and content** — default `align-content:stretch` splits the leftover viewport height BETWEEN the auto rows: `md:grid-cols-[200px_1fr]` → `grid-cols-1` puts the collapsed sidebar/tab-row and the page in two auto rows and deals half the slack to the gap.
